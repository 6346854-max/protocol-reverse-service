# 案例 03：压缩帧长连接的离线分析工具链

> 交付物类型：分析工具 + 解析器 + 帧格式文档
> 关键技术：压缩帧边界切分 · 多层嵌套协议解析 · 帧格式自动识别 · 批量对拍验证
> 状态：已完成，工具在生产环境验证通过

---

## 需求背景

场景是：已经抓到了一份长连接的二进制通信记录，需要从中提取结构化事件。

难点不在"抓"（抓包工具就能解决），而在于**抓下来的东西看不懂**：

- 是二进制帧，不是文本
- 帧体是压缩的
- 解压后是多层嵌套的二进制协议
- 没有协议定义文件

需求方要的是：**把这份二进制记录变成可读、可查、可分析的结构化数据**，并且工具要能复用到后续的记录上。

---

## 技术难点

### 难点 1：压缩帧无法按内容定位边界

离线分析时，帧是裸拼接的（没有长度前缀）。常规做法是扫描协议特征字节来切分帧：

```
扫描 → 发现特征字节 → 读长度 → 切出一帧 → 继续
```

**但帧体是 gzip 压缩的，压缩流里根本找不到原始协议特征字节。**

这是整个项目最卡的一个点。表现是：扫描 0 帧，工具完全不动。

**解法**：既然压缩流里找不到特征，就换锚点——**用 gzip 自己的魔数**：

```
扫描 gzip 魔数 (1f 8b) 作为候选帧起点
    ↓
尝试解压
    ↓
校验解压结果是否符合协议结构
    ↓
不符合则调整边界重试（流式解压可精确定位消耗长度）
```

关键改进是用**流式解压对象**：它能告诉你解压到哪一段就结束了（`unused_data`），从而精确算出这一帧的字节长度，为下一帧定位起点。

### 难点 2：帧格式不止一种

实际抓到的记录里混了多种情况：

| 情况 | 特征 | 处理方式 |
|---|---|---|
| 带长度前缀 | 4 字节小端长度 + 帧体 | 直接按前缀切 |
| 裸拼接 + 压缩 | gzip 魔数 | 魔数扫描 + 流式解压 |
| 裸拼接 + 未压缩 | 协议特征字节 | 特征扫描 + 结构校验 |
| 单帧文件 | 无明显边界 | 整体当一个帧处理 |

**解法**：工具支持三种模式（`--lenpfx` / `--auto` / `--walk`），自动识别或手动指定。

### 难点 3：多层嵌套，且外层容器可能不存在

报文结构：

```
帧体
  └─ 外层容器（protobuf）—— 某些格式下有，某些没有
      └─ 中间层（protobuf）
          └─ 消息列表，每条含 类型标识 + 消息体
              └─ 业务消息体（protobuf）
```

**"外层容器可能不存在"这一点很关键**——不能假设固定层数，必须做兼容：

```python
# 先尝试按外层容器解析，取不到就按当前层直接解析
inner = extract_field(payload, 8) or payload
```

### 难点 4：字段号 ≥ 16 时 tag 占两字节（同一个坑踩了两次）

在第一版解析器里，tag 被当成单字节读：

```python
tag = b[i]        # 错误
i += 1
```

protobuf 的 tag 是 `(字段号 << 3) | wire_type`，本身是 **varint**：

- 字段号 ≤ 15 → tag 占 1 字节
- **字段号 ≥ 16 → tag 占 2 字节或更多**

后果：**16 号以后的所有字段全部错位**。表现出来是某些字段永远读成空值，很容易误判成"服务端没下发这个字段"。

这个坑在案例 01 里踩过一次，在本项目的独立实现里又踩了一次——**说明它不是偶然，而是 protobuf 裸解析的必踩点**，值得单独记录。

### 难点 5：字节偏移和节内偏移的区别（同类错误的另一形态）

在二进制文件分析里，遇到几乎相同性质的坑：**同一个数值在不同上下文里有不同含义**。

以符号表里的地址为例，它可能是：
1. 虚拟地址（需经程序头映射回文件偏移）
2. 节内偏移（节基址为 0 时）
3. 已经是文件偏移

**处理方式（早期版本，有问题）**：用"该位置是否有非零数据"来判断。

**为什么错**：文件头本身就是一堆非零字节，会被误判成代码。结果是拿文件头当指令执行。

**正确做法：确定性规则，不靠猜**：

```
① 若该值落在可执行节范围内     → 判为节内偏移
② 若该值落在某个加载段范围内   → 判为虚拟地址，按映射换算
③ 否则若该值小于文件大小       → 判为文件偏移
```

并附上判断依据一起输出，让人能核对，而不是黑盒。

## 技术方案

### 架构

```
┌─ 帧切分层 ──────────────────────────┐
│ 模式 1: 长度前缀切分                  │
│ 模式 2: gzip 魔数 + 流式解压回溯      │
│ 模式 3: 协议特征扫描 + 结构校验        │
└──────────────────┬──────────────────┘
                   ↓ 独立帧
┌─ 解析层 ────────────────────────────┐
│ gzip 解压                            │
│ 容器层兼容（存在/不存在都处理）        │
│ 消息列表遍历（类型 + 消息体）          │
│ protobuf reader（varint tag）         │
└──────────────────┬──────────────────┘
                   ↓ 结构化事件
┌─ 输出层 ────────────────────────────┐
│ 按类型分类统计                        │
│ 字段全量 dump（用于 schema 校准）      │
│ 判定结论（字段是否实际下发）           │
└─────────────────────────────────────┘
```

### 关键设计决策

| 决策 | 理由 |
|---|---|
| **三种切分模式并存** | 实际数据格式不统一，工具必须兼容而不是要求数据配合 |
| 流式解压对象定位边界 | `unused_data` 能精确给出消耗长度，比猜边界可靠 |
| 容器层做存在性兼容 | 不假设固定层数，`or` 回退 |
| tag 用 varint 解析 | 这是硬性正确性要求，不是优化 |
| 离线分析优先 | 抓包一次，分析可以反复做，不用重抓 |
| 测试样本自己生成 | 没有真实样本时，**自己构造符合格式的样本**才能验证解析器 |

### 最后一招：自己造样本验证

这个项目里有个方法值得单独说——**当拿不到真实样本时，自己构造**：

```
写一个生成器，按真实格式构造：
  · 合法的文件头
  · 正确的节头
  · 真实的符号表 + 字符串表
  · 内嵌可检测的特征字节（加密常量、保护标记等）

然后：
  1. 用工具解析 → 验证识别能力
  2. 用已知答案对拍 → 验证解析正确性
```

**收益**：
- 解析逻辑可回归测试（改代码不会悄悄破坏）
- 没有真实样本也能开发和验证
- 给客户演示时不需要拿真实目标

本项目里这个做法直接抓出了 3 个 bug：
- 字符串表选错（两个节的类型码相同，取了第一个导致解析出 0 个符号）
- 地址语义判断错误（拿文件头当代码执行）
- 指令编码错误（源寄存器没移入正确位置）

**这些都是"跑起来才知道"的 bug，光读代码看不出来。**

## 遇到的问题与解法

| 问题 | 现象 | 根因 | 解法 |
|---|---|---|---|
| **压缩帧扫不出帧** | 离线模式返回 0 帧 | 压缩流里找不到原始协议特征字节 | 改用 gzip 魔数 + 流式解压回溯定位边界 |
| **字段号 ≥16 全部错位** | 部分字段永远读成空值 | tag 当单字节读，实为 varint | tag 用 varint 解析 |
| 符号解析只得到 2 个 | 应该有 21 个符号 | 两个节的类型码相同，取了错误的字符串表 | 通过节链接字段正确定位 |
| 拿文件头当代码执行 | 执行立即异常，寄存器未变 | 地址语义判断靠"是否非零"猜测 | 改为确定性三级判定 |
| 指令编码错误 | 返回值是参数地址而非计算结果 | 源寄存器未移入正确位段 | 逐条反汇编核对 |
| 函数跑不完 | 死循环，达到指令上限 | 多参数函数的第二个参数拿到的是缓冲区地址而非长度值 | 改用单参数入口验证链路 |

## 可复用的产出

1. **压缩帧边界切分模式** —— 适用于任何"压缩体 + 裸拼接"的离线分析场景
2. **protobuf 变长 tag 正确解析** —— 记录为必踩点，避免重复犯错
3. **地址语义确定性判定** —— 三级规则，可复用到任何二进制格式的地址解析
4. **自造样本验证法** —— 拿不到真实样本时的标准做法，能抓出光读代码看不出的 bug
5. **多模式兼容设计** —— 工具适配数据而不是要求数据适配工具
