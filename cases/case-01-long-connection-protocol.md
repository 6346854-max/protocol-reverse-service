# 案例 01：长连接实时消息协议完整分析

> 交付物类型：协议分析 + 零依赖解析器
> 关键技术：WebSocket 长连接 · gzip 压缩帧 · protobuf 无 schema 解析 · 字段语义校准
> 状态：已完成，工具在生产环境验证通过

---

## 需求背景

需求方需要理解某直播平台的实时消息推送机制，目标是：

- 掌握弹幕、礼物、进场、在线统计四类事件的完整数据结构
- 能够以编程方式接入消息流并持久化
- 明确哪些字段服务端实际下发、哪些字段为空壳

原始的诉求描述很模糊（"想拿到直播间里的消息数据"），没有指定接口、协议或字段。这类需求的第一步永远是**先探清通信架构**——因为不同的架构（长连接推送 vs 轮询拉取 vs 混合）对应完全不同的实现路径。

---

## 技术难点

### 难点 1：四层嵌套的报文结构

消息不是普通的 HTTP JSON，而是四层嵌套：

```
WebSocket 二进制帧
  └─ gzip 压缩体
      └─ PushFrame (protobuf)
          └─ Response (protobuf)
              └─ Message[] (protobuf，每个含 method + payload)
                  └─ 业务消息体 (protobuf，按 method 确定类型)
```

**为什么难**：常规抓包工具只能看到最外层二进制。要往里看，得先解开 gzip，再逐层解析 protobuf。

### 难点 2：没有 .proto 定义

平台不公开 schema。**protobuf 是强类型格式，没有 schema 就只能按字节裸读**——需要自己按 tag（字段号 + wire type）遍历，反推每个字段的含义。

### 难点 3：protobuf tag 是变长编码（本项目踩过最深的坑）

这是整个项目最隐蔽的 bug：

```python
# 错误写法：把 tag 当单字节读
tag = b[i]

# 正确写法：tag 本身是 varint
tag, i = read_varint(b, i)
```

**后果**：protobuf 的 tag 由 `(字段号 << 3) | wire_type` 组成。字段号 ≤ 15 时占 1 字节，但**字段号 ≥ 16 时占 2 字节**。

项目中 `sec_uid` 位于 46 号字段，编码为 `f2 02`。按单字节读会得到：

```
0xf2 = 242 → 字段号 30, wire type 2
```

字段号从 46 错成 30，**16 号以后的字段全部错位**。表现出来是 `sec_uid` 永远读出空字符串——很容易误判成"服务端没下发这个字段"，从而得出完全错误的结论。

**修复方式**：tag 必须用 varint 解析。这个 bug 只有在拿真实报文对拍时才会暴露，光看代码看不出来。

### 难点 4：服务端裁剪字段，需要区分"没下发"和"没解析对"

平台会对不同角色的用户裁剪字段。比如匿名访客的用户对象：

```
uid       = 0        ← 服务端下发的就是数字 0
sec_uid   = ''       ← 空字符串
display_id= ''       ← 空
```

**判断"服务端没下发"还是"我解析错了"**，需要：
1. 用完整的 user 对象（有值的）验证解析器正确
2. 再用同一解析器读空值对象
3. 两者对比才能确认

### 难点 5：断线续传凭证

长连接会断。要保证不丢事件，必须回传服务端下发的续传凭证：

```
cursor        ← 消息游标
internal_ext  ← 扩展凭证
```

**不回写的后果**：重连后只收到一屏消息，之前的全丢。

## 技术方案

### 架构

```
┌─ 采集层 ────────────────────────────┐
│ WebSocket 长连接（多主机轮换）        │
│ 断线重连 + 指数退避                   │
│ cursor/internal_ext 自动回写          │
└──────────────────┬──────────────────┘
                   ↓ 原始帧
┌─ 解析层 ────────────────────────────┐
│ gzip 解压                            │
│ PushFrame → Response → Message 逐层拆 │
│ 零依赖 protobuf reader（按 tag 遍历） │
└──────────────────┬──────────────────┘
                   ↓ 结构化事件
┌─ 落库层 ────────────────────────────┐
│ 热路径零 IO（进内存队列）             │
│ 异步批量落库                         │
│ 复合指纹去重                         │
└─────────────────────────────────────┘
```

### 关键设计决策

| 决策 | 理由 |
|---|---|
| **零依赖 protobuf reader** | 手写按 tag 遍历比引入 protobuf 库快一个数量级（单帧 < 0.5ms），且不需要 .proto 文件 |
| 无 schema 裸解析 | 没有 .proto，裸读是唯一可行路径；同时输出字段表供后续生成 schema |
| 热路径只进 deque | 解析后立刻丢内存队列，落库异步批量。避免 IO 阻塞消息处理导致丢帧 |
| 多主机轮换 | 单连接会被限流踢，4 个备选主机轮换 + 指数退避 |
| gzip 魔数帧切分 | 离线分析裸拼接帧时，无法在压缩流里按 tag 定位边界。改用 gzip 魔数 + 解压后结构校验 + 流式解压回溯 |

### 判定方法论（这套方法可复用到其他目标）

面对未知字段，用三层递进判断：

```
第 1 层：字段是否存在
  → 裸 walk 打印所有 tag + 值

第 2 层：字段值是否有意义
  → 按语义提取（uid 应该是数字、sec_uid 应该是长字符串）
  → 与已知有值样本对比

第 3 层：值是服务端下发还是客户端提交
  → 抓包对比请求侧和响应侧
  → 只在响应出现 = 服务端决定
```

## 遇到的问题与解法

| 问题 | 现象 | 根因 | 解法 |
|---|---|---|---|
| 字段值永远为空 | `sec_uid` 读出来是空串 | tag 当单字节读，字段号 46 被错读成 30 | tag 改用 varint 解析 |
| 离线工具解析出 0 帧 | 裸拼接帧文件扫不出任何帧 | 帧体是 gzip，压缩流里找不到 tag | 改 gzip 魔数 + 结构校验 + 流式回溯 |
| 断线后丢事件 | 重连只收到一屏 | 未回写 cursor/internal_ext | 每次收帧都更新续传凭证 |
| 单连接被限流 | 连一会儿就断 | 服务端对单 IP 连接数限制 | 多主机轮换 + 退避重试 |
| 误把"没下发"当"解析错" | 反复调解析器 | 缺对照组 | 用有值样本先验证解析器正确性 |

## 可复用的产出

这个项目沉淀了三个可复用的东西：

1. **无 schema protobuf 解析模式** —— 任何 protobuf 私有协议都能直接套用
2. **长连接稳定性模式** —— 续传凭证回写 + 多主机轮换 + 热路径无 IO
3. **字段语义判定方法论** —— 三层递进判断，可用于任何未知协议分析
