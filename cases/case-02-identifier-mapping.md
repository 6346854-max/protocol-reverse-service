# 案例 02：应用内多标识符获取与映射

> 交付物类型：字段语义分析 + 数据管道
> 关键技术：标识符语义判定 · Base64 打码解码 · 复合指纹去重 · 错误响应识别
> 状态：已完成

---

## 需求背景

需求方的诉求经过了三轮修正才清晰，这个过程本身就值得记录：

| 轮次 | 原始诉求 | 实际问题 |
|---|---|---|
| 1 | 「帮我拿到 App 里的用户标识」 | 没说要哪种标识、从哪拿 |
| 2 | 「要用户的数字 ID」 | 不确定这个字段服务端是否下发 |
| 3 | 「那能不能用账号名换 ID」 | 假设了标识符之间可以互转 |

**这类需求最常见的误区**：把不同的标识符当成可以互相换算的东西。

真实情况是：它们都是同一行数据的不同列。不存在 A 列算出 B 列，只能拿到整行。

---

## 技术难点

### 难点 1：搞清标识符之间的真实关系

应用内常见 5 种用户标识，性质完全不同：

| 标识符 | 性质 | 可改性 | 服务端下发情况 |
|---|---|---|---|
| 用户自设账号名 | 展示用，非主键 | 用户可随时改 | 常下发 |
| 系统分配短号 | 辅助标识 | 不可改 | 常下发 |
| **稳定主键** | 真正的唯一标识 | 不可改 | 常下发 |
| **数字内部 ID** | 内部主键 | 不可改 | **多数场景不下发** |
| 应用作用域内 ID | 跨应用隔离 | — | 视场景 |

**关键认知**：这些标识符之间**没有数学关系**，不能从一个算出另一个。只能"用其中一个当查询键，取出整行"。而"查询"这个动作需要过服务端接口。

**验证方式**：实测 8 个方向的互查接口，全部需要签名参数，且**不传任何参数也返回同一个错误码**——证明这是接口级签名门槛，不是参数问题。

### 难点 2：联系方式被打码（本项目最有价值的发现）

需求方在自己帖子里留了联系方式，但是 Base64 打码的：

```
原始: RXhhbXBsZV9XZWNoYXRfSUQ=       （虚构样例）
解码: Example_Wechat_ID
```

**这种打码方式在技术社区极其常见**（防爬虫抓取联系方式）。识别不出来就等于白白丢掉触达机会。

解码的坑在于**误报**：Base64 字母表和普通字符串重叠度很高，随便一段文本都可能"解码成功"但得到乱码。所以必须做**格式校验**：

```
解码后符合邮箱格式       → 判定为邮箱
解码后是 11 位数字        → 判定为手机号
解码后是 5-24 位字母数字  → 判定为账号名
其余                      → 丢弃
```

### 难点 3：错误响应伪装成成功数据

这是最阴险的坑。接口错误时返回的结构里**也有 data 字段**：

```json
{"data": {"message": "forbidden", "prompts": "暂时无法查看个人信息"},
 "status_code": 10033}
```

如果代码逻辑是 `if data: 解析成功` ，就会把这段错误信息当成用户数据去解析。

**正确做法**：三重校验——
1. 检查错误码（非 0 即失败）
2. 检查 data 里有没有 `message` / `prompts` 这类错误特征字段
3. 检查解析出的字段是否符合语义（ID 应该是数字等）

### 难点 4：复合指纹去重

某些场景下关键标识符为空（服务端不下发），只能用可用字段组合出稳定指纹：

```
指纹 = 哈希(稳定主键 | 头像地址 | 昵称 | 等级 | 其他等级字段)
```

**头像地址是其中最可靠的一项**——它通常是 CDN 路径，即使其他字段被裁剪也会下发。

**局限性必须说清**：这种指纹只在**单一会话范围内**有效，跨会话/跨天会重置。

## 技术方案

### 架构

```
┌─ 入口层 ────────────────────────────┐
│ 分享链接解析（含短链展开）            │
│ 直接 ID 输入                         │
│ 任意网址解析                         │
└──────────────────┬──────────────────┘
                   ↓
┌─ 数据获取层 ────────────────────────┐
│ 站点 API（结构化数据优先）            │
│ 页面抓取 + 站点适配器                 │
│ 通用正文提取（兜底）                  │
│ 域名镜像替换（不可达域名自动换源）     │
└──────────────────┬──────────────────┘
                   ↓
┌─ 提取层 ────────────────────────────┐
│ 联系方式提取（明文 + Base64 打码）    │
│ 标识符字段递归扫描                   │
│ 错误响应识别与过滤                   │
└──────────────────┬──────────────────┘
                   ↓
┌─ 输出层 ────────────────────────────┐
│ 标识符映射表                          │
│ 复合指纹生成                         │
│ 结构化落库                           │
└─────────────────────────────────────┘
```

### 关键设计决策

| 决策 | 理由 |
|---|---|
| **站点 API 优先于页面抓取** | 页面能抓到内容不代表内容是对的。本项目踩过：某站页面能抓到 333 字，但全是导航垃圾；走 API 才拿到真正的正文 |
| **错误响应三重校验** | 单靠 `if data` 会把 forbidden 当用户数据 |
| Base64 解码带格式校验 | 不做校验会产出大量垃圾"联系方式" |
| 镜像域名自动替换 | 部分域名直连不可达，硬化替换表让工具在两种网络环境都能跑 |
| 复合指纹作为降级方案 | 关键字段缺失时至少能区分个体，但要明确标注局限 |
| 多级兜底解析 | API → 站点适配器 → 通用提取，任一环节失效不影响整体 |

## 交付内容

| 项目 | 说明 |
|---|---|
| 标识符映射工具 | 输入任意入口（短链/ID/网址），输出该对象的全部可用标识符 |
| 联系方式提取器 | 明文 + Base64 打码，四类格式（邮箱/手机/账号/即时通讯号） |
| 映射关系文档 | 5 种标识符的性质对照表 + 哪些方向可查、哪些不可查 |
| 局限说明 | 明确写出哪些场景下无法获取，以及为什么 |

## 遇到的问题与解法

| 问题 | 现象 | 根因 | 解法 |
|---|---|---|---|
| **错误响应被当成功数据** | 解析出 `message="forbidden"` 当成用户昵称 | 错误响应里也有 `data` 字段 | 三重校验：错误码 + 错误特征字段 + 语义合理性 |
| Base64 误报 | 普通文本被解码成"联系方式" | 字母表重叠 | 解码后强制格式校验，不符合即丢弃 |
| 页面抓到导航垃圾 | 正文全是"首页/注册/登录/广告" | 该站是客户端渲染，服务端只给壳 | 改用站点 API 优先策略 |
| 打码串残留为真值 | 解出正确账号名后，原始打码串也被当成账号 | 未清理原始值 | 解码成功后从原始字段中剔除打码串 |
| 不可达域名报错 | 部分域名连接超时 | 网络环境差异 | 硬化镜像替换表，失败自动换源 |
| 短链 HEAD 请求返回错误码 | 展开短链失败 | 该站对 HEAD 返回错误 | 改用 GET 逐跳跟随 |

## 验证方式

| 验证项 | 方法 | 结果 |
|---|---|---|
| 联系方式提取 | 5 类输入（打码邮箱/打码账号/明文/即时通讯/空） | 全部正确 |
| 错误响应识别 | 构造 forbidden 响应 | 正确拒绝，不误报 |
| Base64 解码 | 邮箱/手机/账号三种编码 | 全部正确解码 |
| 标识符映射 | 真实分享链接 | 正确提取全部字段 |
| 互查方向验证 | 8 个方向的接口实测 | 确认全部需签名，结论可靠 |

## 可复用的产出

1. **Base64 打码联系方式解码器** —— 带格式校验，可直接复用到任何需要提取联系方式的场景
2. **错误响应识别模式** —— 三重校验，适用于所有服务端接口对接
3. **多级兜底解析架构** —— API → 适配器 → 通用提取，任一环节失效不影响整体
4. **标识符性质对照方法论** —— 判断"某个字段能不能拿到"的通用方法
