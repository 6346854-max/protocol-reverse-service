## 这些案例想说明什么

需求方看案例，关心的通常不是"你会什么技术"，而是三个问题：

**1. 你踩过坑吗？**

案例里花最多篇幅写的是**踩坑与根因**，不是功能清单。
比如「protobuf 的 tag 是变长编码，当成单字节读会导致字段号 ≥16 的全部错位」——
这种细节内行一看就知道是真做过，不是抄的。

**2. 你会不会主动说"做不到"？**

案例 02 里明确写了技术局限：部分标识符在特定用户状态下服务端不主动下发，
**这不是技术可解决的问题**。

把边界说清楚，比把能力吹大更让人信任。

**3. 你的产出能复用吗？**

每个案例末尾都列了「可复用的产出」——不是"我做了个项目"，
而是"我沉淀了 N 个可复用的模式"。这说明下次做类似需求会更快。

## 通用方法论（贯穿三个案例）

### 处理未知协议的三层递进判断

```
第 1 层：字段是否存在
  → 裸解析打印所有字段号 + 值

第 2 层：字段值是否有意义
  → 按语义提取，与已知有值样本对比
  → 区分「服务端没下发」和「我解析错了」

第 3 层：值由哪一端决定
  → 对比请求侧和响应侧
  → 只在响应出现 = 服务端决定，客户端无控制点
```

### 拿不到真实样本时：自己构造

```python
# 生成合法的测试样本：
#   · 正确的文件头 / 节表 / 符号表
#   · 内嵌可检测的特征字节
#   · 真实指令编码（如果要测执行链）
#
# 然后：
#   1. 用工具解析 → 验证识别能力
#   2. 用已知答案对拍 → 验证正确性
```

收益：解析逻辑可回归测试；没样本也能开发；给客户演示不用拿真实目标。

三个案例里这个做法累计抓出了 5 个 bug，**全是"跑起来才知道"的类型**。

### 错误响应可能伪装成成功数据

接口错误时返回的结构里**也可能有正常数据字段**：

```json
{"data": {"message": "forbidden"}, "status_code": 10033}
```

`if data:` 这种判断会把错误信息当业务数据解析。必须三重校验：
错误码 + 错误特征字段 + 解析结果的语义合理性。

## 填写新案例的模板

新建 `case-XX-<主题>.md`，按以下结构写：

```markdown
# 案例 XX：<一句话概括>

> 交付物类型：<分类>
> 关键技术：<3-5 个关键技术点>
> 状态：<已完成 / 进行中>

## 需求背景
   需求方原始诉求 + 诉求背后的真实问题

## 技术难点
   每个难点说清「为什么难」，不只说「难」

## 技术方案
   架构图 + 关键设计决策表（每条决策写理由）

## 交付内容
   表格：项目 | 说明

## 遇到的问题与解法
   表格：问题 | 现象 | 根因 | 解法   ← 这一节最重要

## 验证方式
   表格：验证项 | 方法 | 结果

## 可复用的产出
   沉淀下来的模式/工具，说明下次能省多少时间

## 技术栈

## 说明
   脱敏声明 + 边界说明
```

### 脱敏要求（重要）

| 必须删除 | 原因 |
|---|---|
| 客户 / 平台名称 | 客户隐私，也是你的商业信息 |
| 真实域名、接口路径、包名 | 直接暴露目标 |
| 字段原始值、抓包原文 | 可能包含敏感数据 |
| 完整可运行代码 | 说清方法论就够了，方案不外送 |
| 具体报价数字 | 影响后续谈价空间 |

**保留**：技术难点、根因分析、方法论、验证方式、踩坑记录。

> 判断标准：**读完之后别人知道"你会做这类事"，但不知道"具体怎么做"。**
