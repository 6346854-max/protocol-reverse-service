### 案例 1：直播平台实时消息协议完整分析
[详情 →](./cases/case-01-long-connection-protocol.md)

**需求**：分析直播平台的实时消息推送机制，理解弹幕/礼物/进场事件的协议结构。

**难点**：WebSocket 长连接 + gzip 压缩帧 + 多层嵌套 protobuf，且无协议定义文件，服务端还对字段做了裁剪，需要区分哪些字段实际下发、哪些为空。

**做法**：
- 抓取 WebSocket 原始帧，建立 gzip 解包 → 外层容器 → 消息体 的四层解析链
- 无 schema 裸读 protobuf（按 tag + wire type 遍历），反推完整字段表
- 零依赖解析器，单帧解析 < 0.5ms，支持断线续传凭证回写

**交付**：完整字段表 + 零依赖解析器 + 事件时间线记录方案

### 案例 2：应用内多标识符获取与映射
[详情 →](./cases/case-02-identifier-mapping.md)

**需求**：从应用响应中提取用户的多种标识符，并建立对应关系。

**难点**：需求方最初假设标识符之间可以互相换算。实际上它们是同一行数据的不同列，不存在数学关系，只能"用一个当查询键取出整行"——而这个查询需要服务端接口签名。

**做法**：
- 实测 8 个互查方向，确认接口签名门槛（不传参也返回同一错误码）
- 建立多级兜底解析架构：站点 API → 页面适配器 → 通用提取
- 实现打码联系方式解码（Base64 + 格式校验，避免误报）

**交付**：标识符映射工具 + 提取器 + 明确的技术局限说明

### 案例 3：压缩帧长连接的离线分析工具链
[详情 →](./cases/case-03-frame-analysis.md)

**需求**：把已抓取的长连接二进制记录变成可读、可查、可分析的结构化数据。

**难点**：帧体是压缩的，压缩流里找不到原始协议特征字节，常规的按特征切分帧完全失效（扫描结果 0 帧）。

**做法**：
- 改用 gzip 魔数 + 流式解压回溯定位帧边界（用 unused_data 精确定位消耗长度）
- 三种切分模式并存，自动识别帧格式
- 拿不到真实样本时自己构造合法样本，用已知答案对拍验证

**交付**：离线分析工具 + 解析器 + 帧格式文档 + 测试样本生成器

### 三个案例的共同点

每个案例都遵循同一个方法：**先探清架构，再判断可行性，最后才动手实现**。
顶部三个追问贯穿始终：

```
1. 这个字段是否存在？        → 裸解析打印所有字段
2. 这个值是否有意义？        → 与已知有值样本对比
3. 这个值由哪一端决定？      → 对比请求侧与响应侧
```

第三条经常直接决定项目能不能做——**如果关键控制点在服务端，客户端层面就没有干预空间，这跟技术水平无关**。
我会在评估阶段就说清楚，不接注定做不成的活。
